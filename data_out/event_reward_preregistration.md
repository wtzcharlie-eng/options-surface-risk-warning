# 事件级奖励重训：预先登记（写于任何训练之前）

## 动机

当前 DRL 的奖励函数按**旧口径**设计——逐截面记误报，即同一段风险内每多报一条
就多罚一次。而命题方澄清的新口径按**合并后的预警事件**计精确率：
同一段风险内连报十条与只报一条，代价相同。

**奖励与评测口径不一致。** 理论上，按事件级奖励重训应当学出「少而早的高置信预警」，
与新口径的最优策略形态吻合。当前 15-seed 集成是靠**提高置信门槛**（lean=7.0）
把截面级策略近似成事件级的，属事后补救而非训练目标。

## 假设

**H1**：事件级奖励重训后，在新口径下的验证集精确率 ≥ 当前工作点 + 2.0pp。

## 主端点

**验证集**（2025-01~06）上、按同一选点协议（可行域内精确率最大）选出的工作点处，
**新口径事件级精确率**。测试集在判定阶段不参与。

## 判定规则（不可事后更改）

1. 验证集精确率提升 **≥2.0pp** → 认定有效，进入测试集评估（**只评一次**），
   无论结果如何都如实报出。
2. 提升 **<2.0pp** → 认定无效，**不跑测试集评估**，记为负结果。
3. 是否替换交付版，**只依据验证集**判据。

## 混杂控制

- 新旧奖励各训 **3 个 seed**（42/43/44），同超参、同切分、同 epoch 数
- 对照组不复用现有 15-seed 集成（规模不同不可比），而是**用相同 3 个 seed 的旧奖励模型**
- 两组在同一选点协议下各自选工作点，避免"给新模型调参、旧模型不调"

## 预期（写在前面，便于事后对照判断准不准）

**我预计这一条会失败。** 理由有二：

1. 前六条路径（架构 / 选点协议 / 加特征 / 滚动重训 / 召回偏移先验 / 集成扩容）
   全部证伪，其中集成扩容在验证集上明确有效（+1.53pp）却完全不传导到测试集
   （−0.19pp，传导系数 −0.13）。2025-07 之后的 regime 变化使验证期习得的任何东西
   边际价值都接近零。
2. 事件级奖励改的是**训练目标**，而当前已通过提高 lean 达到了近似效果。
   两者可能高度重叠，增量有限。

**写下这条预期，是为了防止实验失败后把"本来也没指望"当成不算一次尝试。**
若结果与预期相反（即真的有效），那是一个更有价值的发现，同样如实报出。

## 实施

- 奖励改动落在 `drl/env.py::RewardSpec`，新增 `event_level` 开关，**默认关闭**
  （不影响既有交付链路与 G0–G10 全部验证门）
- 新模型落 `data_out/drl_evrew/`，**不覆盖交付目录**
- 复现：`python scripts/event_reward_train.py --budget 150`（分批）
  → `python scripts/event_reward_train.py --eval`

## 结果

**未达阈值，且方向为负。** 按预先登记的规则，**未查看测试集**。

| | 验证集选出 lean | 事件级精确率 | 召回 |
|---|---|---|---|
| 旧奖励（逐截面罚误报） | 7.00 | **71.68%** | 76.77% |
| 事件级奖励 | 7.00 | **69.57%** | 75.71% |
| 差 | — | **−2.11pp** | −1.06pp |

预先登记的阈值是 **≥+2.0pp**，实测 **−2.11pp**——不仅没提升，还略降。

### 机理：奖励对齐了口径，却削弱了训练信号

训练日志把原因摆得很清楚。开启事件级计价后，同一 seed 的策略形态明显变化：

- 训练期累计奖励从 **−3904 变成 +3220**（误报罚金大幅减少）
- **预警率从 25.2% 涨到 45.7%**，seed44 的最终预警率高达 49.6%
- 单模型验证精确率从 37.2% 降到 26.3%

也就是说：**把「同段重复误报不再加罚」写进奖励，等于告诉智能体"多报几条不要紧"**，
它就真的学会了滥报。评测口径确实不惩罚同段重复，但**训练需要的信号强度
与评测需要的计价方式不是一回事**——奖励的作用是塑造策略，不是复刻计分板。

原先「逐截面罚误报 + 事后提高置信门槛（lean=7.0）」的组合反而更好：
训练阶段用密集信号学出好的排序，推理阶段再用阈值把它稀疏化。
**这比让模型自己在稀疏奖励下摸索更有效。**

### 与预期的对照

登记时我写明「预计这一条会失败」，理由是前六条路径全部证伪、且事件级奖励与
提高 lean 的效果可能高度重叠。**方向判断对了，但机理猜错了**——
我以为是"增量有限"，实际是"奖励变松导致滥报，反而更差"。
这个机理比原先设想的更有信息量：**它说明奖励函数不应简单对齐评测口径。**

### 这条负结果的位置

这是第七条被证伪的路径。与前六条不同的是，前六条大多"无可测收益"，
这一条是**明确的负收益**，且给出了一条可复用的设计原则：

> 奖励函数的密度应服务于**学习**，评测口径服务于**验收**，两者对齐反而有害。
> 稀疏化应放在推理阶段（调阈值），而不是训练阶段（改奖励）。

### 交付影响

无。`RewardSpec.event_level_fp` **默认关闭**，交付链路与 G0–G10 全部验证门不受影响
（已实测：默认关闭时交付指标 47.4094% / 74.1370% 与落盘逐位一致）。
新模型落在 `data_out/drl_evrew/`，不覆盖交付目录。
